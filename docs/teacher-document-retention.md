# نگهداری و حذفِ مدارکِ دبیری

حکمِ کارگزینی یک **سندِ هویتیِ یک آدمِ واقعی** است. این سند می‌گوید کجا
ذخیره می‌شود، چه کسی می‌بیندش، چه مدت می‌ماند، و چه چیزی پاکش می‌کند.

---

## کجا ذخیره می‌شود

بیرونِ ریشهٔ عمومیِ `uploads/` — پیش‌فرض `private-uploads/teacher-docs`، و روی
هاست `<app>-private/teacher-docs` (یک پله بالاتر از پوشهٔ برنامه، تا آپلودِ
نسخهٔ تازه پاکش نکند).

`lib/teacher/documents.ts` در **هر** خواندن و نوشتن بررسی می‌کند که این مسیر
داخلِ پوشهٔ عمومی نباشد و اگر بود با خطا می‌ایستد — یک `TEACHER_DOCS_DIR`
اشتباه نباید بی‌صدا سند را عمومی کند.

## چه کسی می‌بیندش

فقط مدیر، و فقط از راهِ
`GET /api/v1/admin/teacher-requests/[id]/document` که خطِ اولش
`requireAdmin()` است.

- `document_key` هرگز در هیچ پاسخِ API و هیچ نوعِ سمتِ کلاینت نمی‌آید.
- کلید در هیچ لاگی نوشته نمی‌شود، **جز** یک مورد: وقتی حذفِ فایل پس از حذفِ
  حساب شکست بخورد (پایین) — آنجا لازم است تا بشود پیگیری کرد، و فقط در
  لاگِ سرور می‌ماند.
- هر بار باز شدنِ فایل در `admin_audit_log` با عملِ `teacher.document_view`
  ثبت می‌شود.

---

## چه چیزی و کِی پاک می‌شود

| رویداد | فایل | چرا |
|---|---|---|
| ارسالِ دوبارهٔ مدارک (`needs_revision` → `pending`) | **فایلِ قبلی پاک می‌شود** | نسخهٔ قدیمی دیگر مبنای هیچ تصمیمی نیست |
| ثبتِ درخواست شکست بخورد | **پاک می‌شود** | فایلی که هیچ ردیفی به آن اشاره نمی‌کند |
| درخواست **رد** شود | **می‌ماند** | مبنای تصمیمِ مدیر باید بعداً قابلِ دیدن باشد |
| درخواست **تأیید** شود | **می‌ماند** | سندِ اثباتِ دبیر بودن |
| **حذفِ حسابِ کاربر** | **پاک می‌شود** | پایین |

### حذفِ حساب

`adminDeleteUser` کلیدهای مدارک را **پیش از** تراکنش می‌خواند، چون
`teacher_requests` با cascade می‌رود و با رفتنش تنها چیزی که می‌گفت کدام فایل
مالِ چه کسی بوده هم می‌رود.

ترتیب عمدی است:

1. خواندنِ کلیدها (فقط با `where user_id = ?` — پس فایلِ دبیرِ دیگری هرگز
   در فهرست نمی‌آید).
2. تراکنشِ حذف.
3. حذفِ فایل‌ها، **بعد** از موفقیتِ تراکنش.

اگر مرحلهٔ ۳ شکست بخورد، حذفِ حساب برنمی‌گردد (کاربر واقعاً حذف شده) ولی
یک خطا با رویدادِ `teacher.document.orphaned` و خودِ کلیدها ثبت می‌شود.

## آشتی‌دهنده (reconciler)

```bash
npm run db:check-teacher-docs              # فقط گزارش
npm run db:check-teacher-docs -- --purge   # حذفِ یتیم‌ها
```

قاعده‌اش یک جمله است: **هر فایلی که هیچ ردیفی در `teacher_requests` به آن
اشاره نمی‌کند، یتیم است.**

⚠️ «هیچ ردیفی» یعنی کلِ جدول و نه ردیف‌های یک کاربر. این تنها قاعده‌ای است
که تضمین می‌کند فایلِ زندهٔ دبیرِ دیگری هرگز حذف نشود. (آزموده شد: با دو
فایلِ یتیم و یک فایلِ ارجاع‌شده، `--purge` دقیقاً همان دو تا را برد.)

گزارش دو عدد می‌دهد:

- **یتیم** — فایل هست، ردیف نیست. قابلِ حذف.
- **گم‌شده** — ردیف هست، فایل نیست. حذف نمی‌شود؛ یعنی مدیر نمی‌تواند آن
  پرونده را بررسی کند و باید از کاربر خواسته شود دوباره بفرستد.

### چرا آشتی‌دهنده و نه صرفاً حذفِ درجا

حذفِ درجا سه راهِ یتیم‌سازی را نمی‌پوشاند: قطعیِ بینِ نوشتنِ فایل و نوشتنِ
ردیف، شکستِ حذف هنگام حذفِ حساب، و هر خرابیِ آینده. یک آشتی‌دهندهٔ ساده هر
سه را با یک قاعده می‌گیرد — و هیچ زیرساختِ تازه‌ای (صف، cron، worker) لازم
ندارد.

---

## پیشنهاد برای اجرا روی هاست

ماهی یک بار، یا بعد از هر حذفِ حسابِ دسته‌جمعی:

```bash
npm run db:check-teacher-docs
```

اگر عددِ یتیم صفر نبود، خروجی را ببینید و بعد با `-- --purge` اجرا کنید.

⚠️ پیش از `--purge` مطمئن شوید `TEACHER_DOCS_DIR` همان مسیرِ واقعیِ هاست
است. با مسیرِ اشتباه، فهرستِ «روی دیسک» خالی می‌شود و چیزی حذف نمی‌شود —
بی‌خطر، ولی گمراه‌کننده.
