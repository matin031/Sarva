# استقرار روی MySQL — و راهِ برگشت

این سند برای کسی نوشته شده که در روزِ مهاجرت پای سرور نشسته است. ترتیب
مرحله‌ها عمدی است و پرش از هیچ‌کدام توصیه نمی‌شود.

> **وضعیت این مهاجرت**
>
> کد کامل است و روی MySQL آزموده شده. **انتقالِ دادهٔ واقعی انجام نشده** —
> نه بکاپ تولیدی در دسترس بود و نه دیتابیس زنده‌ای. یعنی مرحله‌های ۴ تا ۷
> این سند هنوز روی دادهٔ سروا اجرا نشده‌اند و اولین اجرایشان روی سرور، اولین
> اجرای واقعی خواهد بود. مرحلهٔ ۰ (تمرین روی کپی) به همین دلیل اختیاری نیست.
>
> جزئیات آنچه آزموده شده و آنچه نشده، در پایانِ همین سند.


## پیش‌نیازها

- MySQL 8.4 (یا 8.0.4x). **MariaDB نه** — اسکیما از نمایهٔ چندمقداری، ستون
  JSON واقعی و collation های `utf8mb4_0900_*` استفاده می‌کند که یا در
  MariaDB نیستند یا معنای دیگری دارند. ابزار انتقال خودش MariaDB را رد
  می‌کند.
- PostgreSQL فعلی هنوز بالا و در دسترس (برای خواندن).
- فضای دیسک: دست‌کم دو برابر اندازهٔ دادهٔ فعلی، چون هر دو دیتابیس هم‌زمان
  وجود خواهند داشت. `docker system df -v` حجم `sarva_pgdata` را می‌گوید.

## ۰. تمرین روی یک کپی — اجباری

هرچه پایین‌تر می‌آید یک بار روی کپی انجام می‌شود، *پیش* از آنکه به سرور
دست بزنید. اگر مرحله‌ای شکست خورد، آنجا جای فهمیدنش است نه وسطِ قطعیِ
سرویس.

```bash
# بکاپ کامل از پستگرسِ تولیدی (بدون قطع سرویس)
docker compose exec db pg_dump -U sarva -Fc sarva > sarva-prod.backup

# روی ماشین خودتان بازیابی‌اش کنید و همهٔ این سند را رویش اجرا کنید.
```

زمانی که مرحله‌های ۴ تا ۷ روی کپی سبز شدند، عددِ «چقدر طول کشید» را
یادداشت کنید. همان عدد است که پنجرهٔ قطعیِ سرویس را تعیین می‌کند.

## ۱. آماده‌سازی تنظیمات

```bash
cp .env.example .env   # اگر .env دارید، فقط بخش دیتابیس را به‌روز کنید
```

سه مقدار تازه لازم است:

```
MYSQL_USER=sarva
MYSQL_PASSWORD=…
MYSQL_DATABASE=sarva
MYSQL_ROOT_PASSWORD=…
```

⚠️ **گذرواژه داخل یک URL می‌نشیند.** `docker-compose.yml` از این مقادیر
`DATABASE_URL` می‌سازد، پس هر نویسهٔ ویژه‌ای باید URL-encoded باشد:

| نویسه | به‌جایش بنویسید |
|---|---|
| `@` | `%40` |
| `:` | `%3A` |
| `/` | `%2F` |
| `?` | `%3F` |
| `#` | `%23` |
| فاصله | `%20` |

`@` بدترینشان است: یک `@` رمزگذاری‌نشده یعنی همه‌چیزِ بعدش نامِ هاست شمرده
می‌شود — پس به‌جای خطا، تلاش برای وصل شدن به یک سرورِ دیگر. ساده‌ترین راهِ
نداشتنِ این دردسر:

```bash
node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"
```

⚠️ متغیرهای قدیمیِ `POSTGRES_*` را **پاک نکنید** تا وقتی مهاجرت را کامل و
راستی‌آزمایی نکرده‌اید. مسیرِ برگشت به آن‌ها نیاز دارد.

## ۲. بالا آوردن MySQL کنارِ PostgreSQL

```bash
docker compose up -d db
docker compose logs -f db     # تا «ready for connections»
```

هر دو دیتابیس هم‌زمان بالا می‌مانند. حجمِ `pgdata` دست‌نخورده است و
`docker-compose.yml` عمداً هنوز تعریفش می‌کند.

⚠️ **جدول‌های منطقهٔ زمانی.** ایمیج رسمی هنگام مقداردهیِ اولیه پرشان می‌کند.
اگر دیتابیس را از جای دیگری آورده‌اید (سرویس مدیریت‌شده، بازیابی از بکاپ)،
یک بار بررسی کنید:

```bash
npm run db:check-tz
```

اگر شکایت کرد:

```bash
docker compose exec db sh -c \
  "mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -u root -p\$MYSQL_ROOT_PASSWORD mysql"
docker compose restart db
```

این مهم است و علتش این است که `CONVERT_TZ` با نامِ ناشناخته **خطا نمی‌دهد؛
NULL برمی‌گرداند**. یعنی گزارش‌های روزانهٔ پنل بی‌صدا خالی می‌شوند و هیچ‌چیز
در لاگ نمی‌آید.

## ۳. ساخت اسکیما و کاربرِ کم‌امتیاز

```bash
DATABASE_URL="mysql://root:$MYSQL_ROOT_PASSWORD@127.0.0.1:3306/sarva" \
  npm run db:migrate
```

بعد کاربرها. **اپ هرگز نباید با `root` وصل شود.**

```sql
-- کاربر اجرای سایت: فقط داده، بدون DDL.
CREATE USER 'sarva'@'%' IDENTIFIED BY '…';
GRANT SELECT, INSERT, UPDATE, DELETE, EXECUTE ON sarva.* TO 'sarva'@'%';

-- کاربر کنسول SQL مدیر: خواندن، به‌علاوهٔ نوشتنی که کنسول اجازه می‌دهد.
-- عمداً جداست تا اگر روزی خواستید کنسول را فقط‌خواندنی کنید، یک GRANT کافی
-- باشد و نه تغییر کد.
CREATE USER 'sarva_console'@'%' IDENTIFIED BY '…';
GRANT SELECT, INSERT, UPDATE, DELETE ON sarva.* TO 'sarva_console'@'%';

FLUSH PRIVILEGES;
```

⚠️ کاربر اجرای سایت عمداً `TRIGGER` و `CREATE TEMPORARY TABLES` **ندارد**.
تریگرها با امتیازِ سازنده‌شان اجرا می‌شوند، پس بدون این امتیاز هم درست کار
می‌کنند — فقط در `information_schema.triggers` دیده نمی‌شوند. `db:check`
این را می‌شناسد و به‌جای «۱۳ تریگر نیست» می‌گوید «دیده نمی‌شوند».

اثبات اینکه اسکیما درست نشسته:

```bash
DATABASE_URL="mysql://root:…@127.0.0.1:3306/sarva" npm run db:check
```

## ۴. سنجشِ پیش از انتقال

```bash
export SOURCE_POSTGRES_URL="postgres://sarva:…@127.0.0.1:5433/sarva"
export TARGET_MYSQL_URL="mysql://root:…@127.0.0.1:3306/sarva"

npm run etl -- preflight
```

هیچ چیزی نمی‌نویسد. آنچه پیدا می‌کند و **باید پیش از ادامه حل شود**:

- رشته‌ای بلندتر از ستونِ مقصد (چون بعضی `text` ها در MySQL `VARCHAR` با
  طول مشخص شده‌اند تا بتوانند index بخورند)
- دو ایمیل که زیر collation مقصد یکی شمرده می‌شوند
- تاریخِ خارج از دامنهٔ `DATETIME` (پستگرس `infinity` دارد، MySQL نه)
- `sql_mode` غیرسخت‌گیرانه در مقصد
- جدولی در مبدأ که در نقشهٔ انتقال نیست

خروجیِ ناصفر یعنی نروید جلو.

## ۵. قطعِ سرویس و انتقال

اینجا و فقط اینجا سایت پایین می‌آید.

```bash
# ۱) نویسنده‌ها متوقف
docker compose stop app proxy
```

⚠️ این مرحله را کوتاه نکنید. ابزارِ انتقال از یک تصویرِ سازگارِ پستگرس
می‌خواند، پس دادهٔ منتقل‌شده *با خودش* سازگار خواهد بود — ولی اگر سایت در
حین انتقال بنویسد، آن نوشته‌ها اصلاً منتقل نمی‌شوند و بی‌صدا گم می‌شوند.

```bash
# ۲) بکاپ تازه، بعد از توقف نویسنده‌ها
docker compose exec db pg_dump -U sarva -Fc sarva > sarva-final.backup

# ۳) انتقال
npm run etl -- migrate
```

اگر قطع شد (برق، شبکه، Ctrl-C)، همان دستور را دوباره بزنید. از checkpoint
ادامه می‌دهد و اول می‌سنجد که مبدأ در این فاصله تکان نخورده باشد. برای دیدنِ
اینکه کجا مانده: `npm run etl -- status`.

## ۶. اثبات

```bash
npm run etl -- verify
```

این دستور ادعا نمی‌کند؛ اثبات می‌کند:

- شمارشِ دقیقِ هر ۳۹ جدول در دو طرف
- checksum محتوای هر جدول، ستون‌به‌ستون، با یک نمایشِ متنیِ یکسان در هر دو
  موتور (نه `md5` داخلِ هر موتور، که نمایش‌های متفاوت را «اختلاف» می‌خواند)
- هر کلید خارجی با یک anti-join واقعی — نه تکیه بر روشن بودن
  `foreign_key_checks`، که دربارهٔ دادهٔ *موجود* هیچ نمی‌گوید
- شمارنده‌های لایک و دیدگاه در برابر ردیف‌های واقعی
- مقدارِ بعدیِ `AUTO_INCREMENT` جدول `jasoos_levels`

خروجیِ ناصفر یعنی **بالا نیاورید**؛ بروید به بخشِ «برگشت».

بعد از سبز شدن:

```bash
DATABASE_URL="mysql://sarva:…@127.0.0.1:3306/sarva" npm run db:check
DATABASE_URL="mysql://sarva:…@127.0.0.1:3306/sarva" npm run db:check-sql
```

## ۷. بالا آوردن

```bash
docker compose up -d --build
docker compose logs -f app
```

entrypoint خودش migration می‌زند، منطقهٔ زمانی را می‌سنجد و حساب مدیر را
بررسی می‌کند.

بعد، با دست:

- [ ] ورود با گذرواژه (هش‌های Argon2id دست‌نخورده منتقل شده‌اند)
- [ ] ورود با گوگل
- [ ] بازیابی گذرواژه و ایمیل تأیید — هر دو روی `CONVERT_TZ` و مهلت‌ها
      تکیه دارند
- [ ] یک سرودهٔ تازه در کلاب + لایک + دیدگاه، و درست بودنِ شمارنده‌ها
- [ ] یک آزمون تا آخر، و نمرهٔ اعشاری در کارنامه
- [ ] پنل مدیر: نمودارهای روزانه **خالی نباشند** (اگر خالی‌اند، برگردید به
      مرحلهٔ ۲ — منطقهٔ زمانی)
- [ ] کنسول SQL: یک `select` ساده، و اینکه `alter table` را رد می‌کند

## برگشت

تا وقتی `pgdata` هست، برگشت گران نیست.

```bash
docker compose stop app proxy

# DATABASE_URL را در .env به پستگرس برگردانید و تصویرِ قبلیِ اپ را بالا
# بیاورید (کدِ پستگرسی در تگ/کامیتِ پیش از این مهاجرت است).
git checkout <کامیتِ پیش از مهاجرت>
docker compose up -d --build
```

دو نکته که این مسیر را باز نگه می‌دارند و نباید نقض شوند:

1. **`pgdata` را پاک نکنید** تا وقتی مهاجرت را چند روز روی تولید ندیده‌اید.
   `docker compose down -v` هر دو حجم را می‌برد. برای پاک کردنِ آگاهانه‌اش،
   بعداً و به‌صراحت: `docker volume rm sarva_pgdata`.

2. **`migrations/` (پستگرس) در مخزن مانده** و نباید حذف شود. بدون آن،
   بازسازیِ اسکیمای پستگرس روی یک سرور تازه ممکن نیست.

⚠️ چیزی که برگشت **برنمی‌گرداند**: هر نوشته‌ای که بعد از مرحلهٔ ۵ روی MySQL
انجام شده باشد. یعنی هرچه دیرتر برگردید، بیشتر از دست می‌رود. اگر verify
قرمز شد، همان‌جا تصمیم بگیرید.

## نگه‌داری

### بکاپ روزانه

```bash
docker compose exec db mysqldump -u root -p"$MYSQL_ROOT_PASSWORD" \
  --single-transaction --routines --triggers --hex-blob \
  --default-character-set=utf8mb4 sarva | gzip > "sarva-$(date +%F).sql.gz"
```

⚠️ `--routines --triggers` **اختیاری نیست.** `mysqldump` تریگرها و رویه‌ها
را به‌طور پیش‌فرض شامل نمی‌کند. یک بکاپِ بدون آن‌ها بی‌هیچ خطایی بازیابی
می‌شود و سایت بالا می‌آید — ولی شمارنده‌های کلاب و `updated_at` دیگر کار
نمی‌کنند و `club_recount` وجود ندارد. این خرابی ماه‌ها بی‌صدا می‌ماند.

⚠️ `--single-transaction` بکاپ را بدون قفل کردنِ سایت سازگار می‌کند، ولی
**فقط برای InnoDB**. همهٔ جدول‌های ما InnoDB اند (`db:check` می‌سنجد).

### آزمودنِ بکاپ

بکاپی که بازیابی‌اش آزموده نشده، بکاپ نیست:

```bash
gunzip -c sarva-2026-01-01.sql.gz | \
  docker compose exec -T db mysql -u root -p"$MYSQL_ROOT_PASSWORD" \
    --default-character-set=utf8mb4 sarva_restore_test
DATABASE_URL="mysql://root:…@127.0.0.1:3306/sarva_restore_test" npm run db:check
```

### به‌روزرسانی نسخهٔ MySQL

نسخه در `docker-compose.yml` پین شده. برای ارتقا، تگ را عوض کنید و:

```bash
docker compose up -d db
docker compose exec db mysql_upgrade -u root -p   # در 8.0.16+ خودکار است
npm run db:check && npm run db:check-sql && npm run db:check-snippets
```

## آنچه آزموده شده و آنچه نشده

**آزموده شده** (روی MySQL 8.0.46 و PostgreSQL 16، با دادهٔ ساختگی):

- هر ۳۹ جدول، ۳۴۶ ستون، ۲ enum، view، ۱۳ تریگر و رویهٔ `club_recount`
- هر ۲۷۶ دستور SQL اپ، با `PREPARE` روی خودِ MySQL
- ۴۶۲ تست واحد
- چرخشِ توکن refresh زیر همزمانیِ ده‌تایی، شمارندهٔ OTP زیر صد حدسِ هم‌زمان،
  و محدودیت نرخ زیر پنجاه درخواستِ هم‌زمان
- گروه‌بندیِ روزانه به وقت تهران، بایت‌به‌بایت برابر با خروجی پستگرس، از
  جمله روی مرزهای ساعت تابستانی
- انتقال ۵٬۷۸۳ ردیف با checksum برابر در هر ۳۹ جدول، دو بار با `SIGKILL`
  قطع و از سر گرفته شده
- اجرای کاملِ اپ با کاربرِ کم‌امتیاز (بدون `TRIGGER`، بدون DDL)، از جمله
  آتش گرفتنِ تریگرها و تریگرِ نگهبانِ `SIGNAL 1644`
- احراز هویت `caching_sha2_password` با گذرواژهٔ واقعی روی اتصالِ بدون TLS

**آزموده نشده:**

- **انتقالِ دادهٔ واقعیِ سروا.** هیچ بکاپ تولیدی یا دیتابیس زنده‌ای در دسترس
  نبود. ابزار روی دادهٔ ساختگی درست کار می‌کند؛ دربارهٔ دادهٔ واقعی فقط
  `preflight` می‌تواند حرف بزند و باید اجرا شود.
- **MySQL 8.4.** آزمون‌ها روی 8.0.46 اجرا شده‌اند چون در محیط توسعه دسترسی
  به مخزن اوراکل نبود. `docker-compose.yml` روی 8.4 پین است چون پشتیبانی
  8.0 تمام شده. تفاوت‌های مرتبط بررسی شده‌اند و هیچ‌کدام مانع نیستند —
  بزرگ‌ترینشان حذفِ `mysql_native_password` است که ما استفاده نمی‌کنیم
  (`caching_sha2_password` آزموده شده). **پس از اولین بالا آمدن روی 8.4،
  این سه را اجرا کنید:** `npm run db:check`، `npm run db:check-sql`،
  `npm run db:check-snippets`.
- **خودِ استکِ داکر.** در محیط توسعه daemon داکر در دسترس نبود، پس
  `docker-compose.yml` و `Dockerfile` از نظر نحوی بررسی شده‌اند ولی build و
  بالا آمدنشان اجرا نشده. مرحلهٔ ۰ (تمرین روی کپی) اولین جایی است که این
  اجرا می‌شود.
