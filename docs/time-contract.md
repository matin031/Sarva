# قرارداد زمان در سروا

این سند پیش از ساختنِ Activity Tracking و نمودارهای روزانه (فاز ۲) نوشته شد،
چون آن دو کاملاً به این قرارداد وابسته‌اند.

اندازه‌گیری‌ها با `npm run db:check-time` انجام می‌شوند — اسکریپتی که **فقط
می‌خواند** و روی هاست production هم بی‌خطر است.

---

## ۱. مسئله‌ای که پیدا شد

`lib/db` به درایور می‌گوید هر `DATETIME` را UTC تفسیر کند:

```ts
timezone: "Z",      // lib/db/index.ts
dateStrings: true,
```

ولی **هیچ‌جا `time_zone`ِ نشست تنظیم نمی‌شود**. اتصال‌ها `pool.on("connection")`
فقط `sql_mode` می‌گیرند.

پس اگر سرور روی `time_zone = SYSTEM` باشد و ساعتِ سیستم UTC نباشد:

| چه چیزی | چه می‌شود |
|---|---|
| `now(6)` و `DEFAULT CURRENT_TIMESTAMP(6)` | وقتِ **محلیِ سرور** می‌نویسند |
| کدِ خواننده | همان را **UTC** می‌خواند |
| `CONVERT_TZ(x, '+00:00', 'Asia/Tehran')` | یک بارِ **دیگر** جابه‌جا می‌کند |

روی ماشینی با ساعت ایران، اختلاف اندازه‌گیری‌شده **۱۲۶۰۰ ثانیه (۳٫۵ ساعت)** بود.

> ⚠️ این اختلاف روی سرورِ آزمونِ ما اندازه‌گیری شد. **وضعیت production
> اندازه‌گیری نشده.** اولین کاری که باید روی هاست انجام شود همین است:
> `npm run db:check-time`.

---

## ۲. کجا خطرناک است و کجا نیست

قاعده‌اش ساده است: **هر جا دو طرفِ مقایسه از یک ساعت بیایند، امن است.**

### امن — هر دو طرف ساعتِ دیتابیس

انقضای OTP، انقضای سشن، پنجرهٔ محدودیتِ نرخ، `created_at > now(6) - interval`.
این‌ها مستقل از منطقهٔ زمانی درست کار می‌کنند، چون هرگز با ساعتِ Node مقایسه
نمی‌شوند.

### امن — هر دو طرف ساعتِ Node

`plus_entitlements.starts_at` / `ends_at`. هر سه مسیرِ اعطا (`activateForOrder`،
`manualGrant`، `grantTeacherPlus`) شیءِ `Date` پاس می‌دهند و `lib/plus/coverage.ts`
هم در جاوااسکریپت مقایسه می‌کند.

> ⚠️ `grantTeacherPlus` تا همین اواخر `now(6)` می‌نوشت و **همین یک ناسازگاری**
> باعث می‌شد اشتراکِ دبیرِ تازه‌تأییدشده تا ۳٫۵ ساعت فعال نشود. حالا مثل دو
> خواهرش `Date` می‌دهد.

### خطرناک — مخلوط

| مورد | وضعیت |
|---|---|
| `rate_limits.reset_at` منهای `Date.now()` | **رفع شد** — حالا با `timestampdiff` در SQL حساب می‌شود |
| `extendEntitlement`: `greatest(ends_at, now(6))` | مخلوط می‌ماند؛ فقط وقتی اثر دارد که اشتراک از قبل منقضی باشد |
| سطل‌بندیِ روزانه با `CONVERT_TZ` | **بستگی به سرور دارد** — پایین |

---

## ۳. مهم‌ترین نکته برای فاز ۲

**همهٔ `answered_at`ها را ساعتِ دیتابیس می‌نویسد** — یا با
`DEFAULT CURRENT_TIMESTAMP(6)` یا صریحاً با `now(6)`:

`user_answers`، `vocab_answers`، `jasoos_answers`، `aruz_bridge_answers`،
`grammar_circuit_answers`، `quiz_attempts`، `exam_attempts`.

و `getPanelOverview` روی همان‌ها `CONVERT_TZ(at, '+00:00', 'Asia/Tehran')` می‌زند.

پس:

- اگر نشستِ سرور **UTC** باشد → درست است.
- اگر **محلیِ ایران** باشد → مقدارِ ذخیره‌شده از قبل تهران است و یک بار دیگر
  ۳٫۵ ساعت جلو می‌رود. نتیجه: **فعالیتِ بعد از ۲۰:۳۰ به روزِ بعد می‌افتد.**
  «روزهای فعال»، «رشتهٔ روزها» و نمودار روزانه همگی کج می‌شوند.

این تنها دلیلی است که این سند باید **پیش از** فاز ۲ حل شود.

## ۴. قرارداد پیشنهادی

| لایه | قرارداد |
|---|---|
| ذخیره‌سازی | **UTC**، در `DATETIME(6)` |
| نشستِ دیتابیس | `time_zone = '+00:00'` روی هر اتصال |
| نوشتن از Node | شیءِ `Date` (درایور با `timezone:"Z"` آن را UTC می‌نویسد) |
| نوشتن در SQL | `now(6)` — که با نشستِ UTC همان UTC است |
| خواندن | `dateStrings: true` + مبدلِ `lib/db` → رشتهٔ ISO با `Z` |
| نمایش | فقط در UI به `Asia/Tehran` تبدیل شود |
| مرزِ روز در گزارش | `CONVERT_TZ(x, '+00:00', 'Asia/Tehran')` — که با ذخیره‌سازیِ UTC درست است |

تغییرِ لازم برای رسیدن به آن، **یک خط** در `pool.on("connection")` کنارِ
`sql_mode` است:

```sql
set session time_zone = '+00:00'
```

> ⚠️ عمداً هنوز **اعمال نشده**. تصمیمش به دادهٔ موجودِ production بستگی دارد
> (بخش بعد) و اجرای خودسرانه‌اش می‌تواند تاریخچه را ناپیوسته کند.

## ۵. اگر production محلی نوشته باشد

### تشخیص

```bash
npm run db:check-time
```

برای هر جدولِ زمان‌دار «فاصلهٔ تازه‌ترین ردیف تا حالا» را می‌دهد. اگر ردیف‌ها
**در آینده** باشند، یعنی محلی نوشته شده‌اند — و مقدارِ جابه‌جایی همان
offsetِ سرور است.

### جدول‌های متأثر

همان‌هایی که در بخش ۳ آمدند، به‌علاوهٔ `sessions`، `users`، `plus_entitlements`،
`teacher_requests`. تعداد دقیقِ ردیف‌ها را همان اسکریپت گزارش می‌کند.

### نقشهٔ backfill (فقط اگر لازم شد)

1. **بکاپ کامل** (phpMyAdmin → Export). بدونِ آن هیچ قدمِ بعدی برداشته نشود.
2. سایت را STOP کنید تا نوشتنِ جدید وسطِ کار نیاید.
3. offset را از `db:check-time` بردارید (مثلاً `+03:30`).
4. برای هر جدول/ستون:
   ```sql
   UPDATE `<table>` SET `<col>` = CONVERT_TZ(`<col>`, '+03:30', '+00:00');
   ```
   ⚠️ با offsetِ عددی و نه نامِ منطقه — تا به جدول‌های tz وابسته نباشد.
5. `set session time_zone = '+00:00'` را در کد فعال کنید.
6. RESTART و دوباره `db:check-time`.

### rollback

- پیش از هر چیز: برگرداندنِ بکاپ.
- اگر بکاپ در دسترس نبود، همان `UPDATE` معکوس (`'+00:00'` → `'+03:30'`) کار
  می‌کند، **به شرطی که** بین backfill و rollback هیچ ردیفِ تازه‌ای نوشته نشده
  باشد. به همین دلیل قدم ۲ (STOP) اختیاری نیست.

### راهِ بدونِ دست زدن به دادهٔ قدیمی

اگر نمی‌خواهید تاریخچه را جابه‌جا کنید، فاز ۲ هم بدونِ backfill شدنی است:

- نشست را روی `'+00:00'` تنظیم کنید (از این به بعد همه‌چیز UTC).
- بپذیرید که داده‌های *پیش از* آن لحظه به اندازهٔ offset جابه‌جا هستند.
- برای گزارش‌ها یک مرزِ زمانی بگذارید و در UI بنویسید «داده‌های پیش از فلان
  تاریخ تقریبی‌اند».

این برای نمودارِ روزانه قابلِ قبول است، چون ارزشِ واقعی‌اش در هفته‌های اخیر
است و نه در سالِ گذشته.

## ۶. پیش‌نیازِ هاست: جدول‌های منطقهٔ زمانی

`CONVERT_TZ` با **نامِ** منطقه (`'Asia/Tehran'`) به جدول‌های `mysql.time_zone*`
نیاز دارد. اگر بارگذاری نشده باشند، تابع به‌جای خطا **NULL** برمی‌گرداند و
نمودار بی‌صدا خالی می‌شود.

روی سرورِ آزمونِ ما بارگذاری **نشده** بودند.

**راه‌حل روی لینوکس:**

```bash
mysql_tzinfo_to_sql /usr/share/zoneinfo | mysql -u root mysql
```

روی هاستِ اشتراکی که دسترسیِ root ندارید، این را از پشتیبانی بخواهید.

**بررسی:**

```sql
SELECT CONVERT_TZ('2026-01-01 12:00:00', '+00:00', 'Asia/Tehran');
-- باید 2026-01-01 15:30:00 بدهد. اگر NULL داد، بارگذاری نشده‌اند.
```

`npm run db:check` و `npm run db:check-time` هر دو همین را می‌سنجند.

### جایگزین اگر بارگذاری ممکن نشد

ایران از سال ۲۰۲۲ ساعتِ تابستانی ندارد، پس برای داده‌های بعد از آن
`'+03:30'` دقیقاً معادلِ `'Asia/Tehran'` است:

```sql
CONVERT_TZ(x, '+00:00', '+03:30')
```

⚠️ برای داده‌های قدیمی‌تر **غلط** است (تا ۲۰۲۲ ساعت تابستانی داشتیم و تابستان‌ها
`+04:30` بود). اگر گزارشی به سال‌های پیش از ۲۰۲۲ برگردد، جدول‌های tz لازم‌اند.

## چیزهایی که در مرحلهٔ ۲ بر اساس همین قرارداد ساخته شدند

هر جدولِ تازه‌ای که از اینجا به بعد آمد، ستونِ زمانش را **برنامه** می‌نویسد
و نه `now(6)` یا `CURRENT_TIMESTAMP`:

| جدول | ستون | چرا |
|---|---|---|
| `user_activity_events` | `occurred_at` | تنها ستونِ بی‌ابهامِ زمانی |
| `teacher_student_views` | `viewed_at` | همان |
| `teacher_feedback` | `created_at` / `updated_at` | همان |

درایور یک `Date` را همیشه UTC می‌فرستد (`timezone: "Z"` در `lib/db`)،
مستقل از تنظیمِ سرور. پس این ستون‌ها **از روزِ اول** درست‌اند و هر تصمیمی
که بعداً دربارهٔ دادهٔ قدیمی گرفته شود، به آن‌ها کاری ندارد.

⚠️ `user_activity_events.created_at` استثناست و عمداً ساعتِ **دیتابیس** را
می‌نویسد. اختلافِ آن با `occurred_at` یک اندازه‌گیریِ همیشگی و رایگان از
همان چیزی است که هنوز نمی‌دانیم:

```sql
SELECT MAX(TIMESTAMPDIFF(SECOND, occurred_at, created_at))
  FROM user_activity_events;
```

صفر یعنی نشست UTC است. ۱۲۶۰۰ یعنی سرور روی تهران است. هیچ تحلیلی از
`created_at` نمی‌خواند.

### گزارش‌های روزمحور، در برابرِ نبودنِ جدول‌های tz

`lib/analytics/timezone.ts` یک بار در هر فرایند می‌سنجد که
`CONVERT_TZ(..., 'Asia/Tehran')` جواب می‌دهد یا نه. اگر نه:

- تحلیلِ **غیرروزانه** دست‌نخورده کار می‌کند (دقت، وزن، نقش، شمارش‌ها،
  آخرین فعالیت) — هیچ‌کدام `CONVERT_TZ` نمی‌خواهند.
- بخشِ روزمحور یک وضعیتِ **صریحِ `unavailable`** می‌گیرد و نه یک آرایهٔ
  خالی. رابط کاربری همان جمله را نشان می‌دهد.
- یک بار با رویدادِ `analytics.timezone_unavailable` لاگ می‌شود.

⚠️ این یک احتیاطِ نظری نیست. پیش از این، `getPanelOverview` همهٔ ردیف‌ها را
در یک سطلِ `NULL` می‌ریخت و «روزهای فعال» **یک** می‌شد، هرقدر هم کاربر
فعال بوده باشد — یک عددِ غلط و نه یک نمودارِ خالی. روی MariaDB 10.11
اندازه‌گیری شد.

## `extendEntitlement` — بررسی‌شده، عمداً تغییر نکرده

```sql
set ends_at = date_add(greatest(ends_at, now(6)), interval ? day)
```

`ends_at` را برنامه می‌نویسد (UTC) و `now(6)` ساعتِ سرور است. اگر آن دو
یکی نباشند، `greatest` دو چیزِ ناهم‌مقیاس را می‌سنجد.

**اندازه‌گیری‌شده** روی سرورِ آزمون با اختلافِ ۱۲۶۰۰ ثانیه
(`npm run db:check-time`، بخش ۴):

| وضعیت | نتیجه |
|---|---|
| اشتراکی که یک ساعت دیگر تمام می‌شود | عبارت آن را **منقضی** می‌بیند |
| پس تمدید از ساعتِ سرور شمرده می‌شود | کاربر تا ۳٫۵ ساعت **بیشتر** می‌گیرد |

جهتِ خطا با علامتِ اختلاف عوض می‌شود:

- سرور **جلوتر** از UTC (مثل ایران) → کمی بیشتر، به نفعِ کاربر.
- سرور **عقب‌تر** از UTC → اشتراکی که تازه منقضی شده از لحظهٔ انقضا تمدید
  می‌شود و کاربر همان اندازه **کمتر** می‌گیرد.

### چرا هنوز عوض نشده

راهِ درست همان کاری است که `grantTeacherPlus` شد: به‌جای `now(6)` یک
`Date` از Node پارامتر شود.

⚠️ ولی این فقط وقتی درست است که `ends_at`های **موجودِ production** خودشان
UTC باشند. اگر با ساعتِ محلی نوشته شده باشند، مقایسهٔ آن‌ها با یک `Date`ِ
UTC خطا را برعکس می‌کند — و آن‌وقت به‌جای یک سوگیریِ کوچکِ به‌نفعِ کاربر،
یک سوگیریِ به‌ضررِ او می‌سازیم.

پس ترتیبش این است:

1. روی هاست: `npm run db:check-time` — بخش ۳ می‌گوید دادهٔ موجود محلی
   نوشته شده یا UTC.
2. اگر UTC بود: پارامترِ `Date` جایگزینِ `now(6)` شود. تغییرِ بی‌خطر.
3. اگر محلی بود: اول تصمیمِ backfill (بالای همین سند)، بعد این.

تا آن موقع اثرش حداکثر چند ساعت روی تمدیدهای **دستیِ** مدیر است — و
`grantTeacherPlus`، که مسیرِ خودکار و پرتکرار است، از قبل درست شده.
