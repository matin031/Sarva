# انتقال دامنه: عروضینو ← سروا

سندِ اجرایی. هر کاری که به دسترسیِ مالک نیاز دارد اینجا **چک‌لیست** است، نه
کارِ انجام‌شده. هیچ‌کدام از این مراحل توسط من اجرا نشده است.

---

## ۱. یافتهٔ اصلی: مسیرها عوض نمی‌شوند

پیش از ساختنِ هر جدولِ ریدایرکتی، این را بررسی کردم:

```
git log --diff-filter=A --name-only -- 'app/**/page.tsx'   →  ۵۲ مسیر
find app -name page.tsx                                    →  ۵۲ مسیر
تفاوت: هیچ
```

**در تمامِ تاریخچهٔ این مخزن، هیچ مسیری حذف یا تغییرِ نام نداده.** عروضینو و
سروا یک کدبیس‌اند؛ آنچه عوض می‌شود فقط نامِ دامنه است.

نتیجهٔ عملی: انتقال **مسیر‌به‌مسیر و یک‌به‌یک** است.

```
https://aruzino.ir/<هر مسیری>  →  https://sarvaedu.ir/<همان مسیر>
```

نه جدولِ نگاشتِ دستی لازم است، نه استثنا. و مهم‌تر: **هیچ آدرسی به صفحهٔ خانه
فرستاده نمی‌شود** — که خواستهٔ صریحِ شما بود و رایج‌ترین اشتباهِ این نوع
مهاجرت است (اعتبارِ هر صفحه را دور می‌ریزد و برای کاربر هم گیج‌کننده است).

> ⚠️ این نتیجه از تاریخچهٔ *کد* می‌آید. اگر عروضینو روزی روی کدِ دیگری اجرا
> شده یا مسیرهایی خارج از این مخزن داشته (مثلاً یک وبلاگ یا صفحهٔ فرود
> جداگانه)، آن‌ها در این بررسی نیستند. مرحلهٔ ۵ همین سند برای پیدا کردنشان
> است.

---

## ۲. ⚠️ جهتِ www باید برگردد — پیش از هر چیزِ دیگر

شما `sarvaedu.ir` را دامنهٔ اصلی انتخاب کردید و کد بر همان اساس تنظیم شد.

ولی در بررسیِ اولیه، سایت **برعکس** رفتار می‌کرد:

```
امروز:   sarvaedu.ir  →  www.sarvaedu.ir
باید:    www.sarvaedu.ir  →  sarvaedu.ir
```

اگر این برنگردد، هر `canonical` سایت به آدرسی اشاره می‌کند که خودش ریدایرکت
می‌شود. این بدترین حالتِ ممکن است: موتور جست‌وجو سیگنالِ متناقض می‌گیرد و
canonical عملاً بی‌اثر می‌شود.

**این تغییرِ وب‌سرور و تغییرِ کد باید با هم منتشر شوند.**

نمونه برای Caddy:

```caddyfile
www.sarvaedu.ir {
    redir https://sarvaedu.ir{uri} permanent
}

aruzino.ir, www.aruzino.ir {
    redir https://sarvaedu.ir{uri} permanent
}

sarvaedu.ir {
    reverse_proxy localhost:3000
}
```

`{uri}` مسیر و کوئری را دست‌نخورده می‌برد — همان چیزی که «انتقالِ مستقیم به
صفحهٔ متناظر» را ممکن می‌کند.

## ۳. متغیرِ محیطی

```bash
NEXT_PUBLIC_SITE_URL=https://sarvaedu.ir
```

تنها منبعِ آدرس در کل پروژه همین است (`lib/seo/site.ts`). اگر تنظیم نشود،
پیش‌فرض همین مقدار است — ولی صریح تنظیمش کنید تا در پیش‌نمایش‌ها هم رفتار
معلوم باشد.

برای پیش‌نمایش/staging:

```bash
NEXT_PUBLIC_SITE_URL=https://preview.example.ir
SEO_NOINDEX=true
```

`SEO_NOINDEX` عمداً فقط با رشتهٔ `true` فعال می‌شود و در production تنظیم
نمی‌شود، تا هیچ‌وقت به ارث نرسد و بی‌صدا کلِ سایت را از نتایج بیرون نیندازد.

## ۴. ترتیبِ اجرا

| # | کار | جای اجرا |
|---|---|---|
| ۱ | `NEXT_PUBLIC_SITE_URL=https://sarvaedu.ir` | env سرور |
| ۲ | برگرداندنِ جهتِ www (بخش ۲) | وب‌سرور |
| ۳ | ریدایرکتِ دائمیِ عروضینو با حفظ مسیر | وب‌سرور |
| ۴ | انتشار کد | — |
| ۵ | `node scripts/check-seo.mjs https://sarvaedu.ir` | هر جا |
| ۶ | تأییدِ **هر دو** دامنه در Search Console | Search Console |
| ۷ | ابزار Change of Address از عروضینو به سروا | Search Console |
| ۸ | ارسال `https://sarvaedu.ir/sitemap.xml` | Search Console |

منتقل می‌کند، ولی لینک‌هایی که از بیرون به عروضینو داده شده تا سال‌ها زنده
می‌مانند. برداشتنِ زودهنگامِ ریدایرکت یعنی دور ریختنِ همهٔ آن‌ها.

## ۵. فهرستِ آدرس‌های واقعیِ عروضینو

تحلیلِ بالا از کد می‌آید. برای اطمینان، فهرستِ چیزی که گوگل *واقعاً* از
عروضینو می‌شناسد را هم بگیرید:

**راهِ اول — Search Console** (دقیق‌ترین)
Search Console ← دامنهٔ عروضینو ← Indexing ← Pages ← دکمهٔ Export.

**راهِ دوم — sitemap خودِ عروضینو**

```bash
curl -s https://aruzino.ir/sitemap.xml | grep -o '<loc>[^<]*</loc>' \
  | sed 's|</\?loc>||g' > aruzino-urls.txt
wc -l aruzino-urls.txt
```

بعد بررسی کنید که هر کدام روی دامنهٔ تازه هم ۲۰۰ می‌دهد:

```bash
while read -r u; do
  path=$(echo "$u" | sed 's|https\?://[^/]*||')
  code=$(curl -s -o /dev/null -w "%{http_code}" -L "https://sarvaedu.ir$path")
  [ "$code" = "200" ] || echo "$code  $path"
done < aruzino-urls.txt
```

هر چه چاپ شود، آدرسی است که مقصدِ متناظر ندارد. اگر تعدادشان کم بود
مسیرِ درستش را بگویید تا نگاشتِ صریح اضافه کنم؛ اگر محتوایش واقعاً حذف شده و
جایگزینی ندارد، **۴۱۰** مناسب‌تر از ریدایرکت به صفحه‌ای نامرتبط است.

## ۶. آزمونِ سلامتِ ریدایرکت‌ها پس از اجرا

```bash
# باید ۳۰۱ بدهد و مستقیم به مقصد برسد — نه زنجیره، نه حلقه
for p in / /aruz /vazn-yab /doroos/yazdahom/1 /game/ninja /guide; do
  printf '%-28s ' "$p"
  curl -s -o /dev/null -w '%{http_code} → %{redirect_url}\n' "https://aruzino.ir$p"
done
```

انتظار: هر خط `301 → https://sarvaedu.ir<همان مسیر>`.

نشانه‌های خطر:
- `302` به‌جای `301` — موقتی است و اعتبار را منتقل نمی‌کند.
- بیش از یک پرش (`aruzino → www.aruzino → www.sarvaedu → sarvaedu`).
- هر مقصدی که خودش `/` باشد در حالی که مسیرِ مبدأ `/` نبوده.

---

## ۷. کاری که *نباید* کرد

- **همزمان با مهاجرت، ساختارِ URL را عوض نکنید.** اگر بعداً مسیری باید عوض
  شود، بگذارید برای بعد از پایدار شدنِ انتقال — وگرنه هیچ‌وقت معلوم نمی‌شود
  افتِ احتمالی از کدام تغییر بوده.
- **`robots.txt` عروضینو را `Disallow: /` نکنید.** خزنده باید بتواند
  ریدایرکت را ببیند؛ مسدود کردنش دقیقاً جلوی انتقالِ اعتبار را می‌گیرد.
- **دامنهٔ قدیم را رها نکنید.** بخش ۹ بالا.
